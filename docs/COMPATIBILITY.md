# 版本升级与适配规则

## 两类升级

- **模块升级**：相同包名、相同签名、递增 versionCode 的 APK 直接覆盖安装，重启抖音。通知头像涉及 System UI 时才需要重载该进程。
- **抖音升级**：不能只替换版本号或取消版本判断。先检查反射接口、资源结构、主题模型和页面生命周期，再决定是否复用已有适配。

## 稳定逻辑与版本差异

通用引擎负责窗口沉浸、实时系统栏 Insets、布局所有权、键盘避让、主题调度、动画与触摸。相同结构尽量复用适配器；不同页面使用同一容器，并不自动代表其父级 Insets 与窗口策略相同。

版本差异应逐步集中在兼容配置/适配层，包括主界面 delegate、标签恢复策略、主题数据类、Compose 渲染类与可选旧版业务补丁。新增支持先核验接口，再启用对应配置；单项补丁失败应隔离，避免关闭全部主题同步。

**现状**：0.3.17 已复用多类结构适配器，但 40.7/40.8 的差异仍有部分版本分支位于主题与个人页修正中；统一的版本配置层尚未完成，属于后续重构方向，不应宣传为已经实现。

## 每次升级的检查顺序

1. 记录抖音 versionName/versionCode、设备系统、模块版本与构建提交。
2. 核验必需反射方法的参数、返回值与字段语义，不能仅核验类名存在。
3. 核验首页、消息、聊天、评论、搜索/历史进入的视频与图文、音乐/玩法、听抖音的容器复用与实际 Insets。
4. 同一目标只保留一个几何写入者；保留原始 padding/margin/translation，并在失去所有权时恢复。
5. 回归键盘打开关闭、表情面板、聊天快速回到底部的进入/退出/滚动中点击，以及系统浅深色双向热切换和会话恢复。
6. 仅记录实际覆盖范围；独立补丁不兼容时明确降级与限制，不把未验证版本标为全面支持。

## 后续重构约束

- 不以全局 DPI、硬编码抬高像素或逐页面重复平移代替 Insets 适配。
- 不同时运行多个模块去修改同一个布局目标。
- 不为应用更新重启 System UI；保留包名、设置键和官方签名以支持覆盖安装。
- 不提交设备日志、聊天截图、原始抖音 APK、用户标识与签名材料。
